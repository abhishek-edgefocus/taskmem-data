- 2026-07-20T15:54Z [claude-code] INTERVAL VAR FEASIBILITY (asked 2026-07-20 'is it possible to fix the interval?'). Read all 9 panels' SQL. Answer: possible but NOT a single parameter swap — it splits into 3 classes with a real semantics decision at the centre, and one panel cannot honour 'Daily' at all. CLASS A, mechanically easy (4 panels: 599, 607, 622, 624 'Avg. \$Interval'): pure 'SELECT AS_OF_DATE AS time, SUM(...) FROM GOLD.POSITIONS_DAILY ... GROUP BY AS_OF_DATE'. Wiring = DATE_TRUNC(unit, AS_OF_DATE) in SELECT+GROUP BY, and change the var values from the legacy MySQL strftime strings (%Y-%m-%d / %Y-%m-01, a leftover from the datastore dashboard) to Snowflake units (DAY/MONTH). SEMANTIC TRAP: these are STOCK metrics (DPD_COUNT_*, DPD_PRINCIPAL_* = a snapshot of the book each day), so rolling to monthly with SUM would ~30x them. Correct monthly is AVG over the month (the titles literally say 'Avg.') or a month-end snapshot — a decision, not a mechanical edit. 622/624 are ratios SUM(a)/NULLIF(SUM(b)) so monthly needs avg-of-daily-ratios vs ratio-at-month-end chosen deliberately. Its title is bare '\$Interval', so today it renders as 'Daily' while showing monthly data — the most clearly wrong instance. CLASS C, hard (484 'Expected \$Interval', 486 '\$Interval'): refId B_SF deliberately EXPANDS monthly predicted cashflows into a daily step function (monthly_agg CTE with DAY(LAST_DAY(...)) days_in_month divisor).
