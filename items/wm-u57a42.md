PR #6462 (DEV-1498, [[wm-79k8df]]) was validated by running the transform's own
module CLI and the predictors in-process against `DEV_ABHISHEK`. The Dagster
wiring was checked **only statically** — `orchestration/scripts/check_definitions.py`
passes and `northpond_api_credit_attributes` resolves inside
`ingest_api_output`'s selected asset keys — but the asset has never actually
been materialized. Abhishek asked for this directly on 2026-08-26.

**Three things to prove, in order:**

1. **Materialize `northpond_api_credit_attributes`** through the local Dagster on
   dpx against `DEV_ABHISHEK`. Expect 715 rows on CHANNEL `northpond_loan_fl`
   and ~536 on `northpond_exp_loan_fl` (DEV lags PROD by a few days; PROD's SQL
   returns 579), 0 duplicate `(EFP_ID, AS_OF_DATE)` keys, 0 nulls in
   `AMOUNT`/`TERM`/`RATE`/`MONTHLY_PAYMENT`/`PAYLOAD`. Capture the run URL — the
   PR style guide wants the run id, not "it ran".

2. **Settle the `API_CREDIT_ATTRIBUTES_STREAM` question.** The direct CLI run
   wrote its rows and then failed on `consume_stream`:
   `Object 'DEV_ABHISHEK.SILVER.API_CREDIT_ATTRIBUTES_STREAM' does not exist`.
   The stream is declared in `terraform/snowflake/silver_api_credit_attributes.tf`
   and does exist in PROD (created 2026-06-25, owner `PROD_WRITER`). Because it
   sits on the **shared** target table, the likely reading is DEV terraform drift
   that would hit sofi/prosper/upgrade/anchored/openroad identically — but that
   is an inference, not a check. Confirm by looking for the stream in DEV and by
   trying any other platform's credit-attributes asset. If it really is drift,
   `tf-apply` against DEV and re-run; if it is not, the transform has a real
   problem, because it has then never completed a clean run anywhere.

3. **Close the parquet round trip.** Predictions were written to
   `s3://efp-sandbox/abhishek/dev-1498/` and read back with pandas for the parity
   diff. They were never ingested through `ingest_prediction_files` →
   `s3_prediction_files` → `s3_predictions` → `silver.predictions`. Nothing yet
   proves the rows land in `silver.predictions` with the right schema, or that
   `predicted_cashflows` consumes them. This is the biggest untested seam in the
   PR and the one most likely to hide a surprise.

Until 1–3 are done the PR stays draft — its Testing section overstates coverage
by saying "validated in DEV_ABHISHEK" without these caveats, so the body needs a
correction pass in the same sitting.
